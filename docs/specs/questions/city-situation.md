- **CS18 - §4.6 `get_success_count` / `activate_situation`: string GUID conversion (CS13 follow-up).** The registry mirror converts Lua strings to RZCharArray variants (lua-host §9.3), and the first twelve actual `get_success_count` inputs in the Jinae fixed schedule all have that type (`0x800E`). Numeric conversion yielded GUIDs such as 0, 2, 4, 6 and 8, so it cannot identify the missions. What is the original string-to-GUID conversion: hexadecimal with an optional `0x` prefix, or another format; and what happens for malformed strings or numeric arguments? The implementation now chooses hexadecimal strings and truncates numeric Float64 arguments, marked SPEC-GAP. Please also confirm the success-count result's variant type and the optional briefing default. Evidence: qcheck-18.log, Jinae run compare-20261028-035655-2829c710; remaining advisor activation flags differ for GUIDs 4C142F8A, 4C14354A, 8C03EC4A, AC143545, AC1726C8 and CC1435A1. No callback for the original manager is forwarded.

- **CS19 - §8 slot 16 output-object construction and no-target behaviour.** Is the single pointer argument to `GetCurrentTargetName` a constructed `cIGZString&`, or hidden result storage that the callee must construct? Please specify how the output is initialized and populated when no mission/target is active, and the return/ownership contract. Correct hexadecimal GUID parsing activates mission advice whose native text detokenizer calls this slot. Our former void declaration, leaving output untouched, was followed by an AV at SimCity 4.exe+0x50E210 reading null. Returning `&out` in EAX as §8 requires moves the AV to +0x50E219 reading 0x1C; it does not fix it. No original slot implementation is forwarded. Final qcheck-21.log: Jinae corrupt at 2047-04-12 (compare-20261028-042001-b6169111), East Weburg corrupt at 2112-06-21 (compare-20261028-042001-f8aee19f); one foreign exception each, ref_warnings=0. Konradshohe churn and Rush Hour are exact with this same build; original-only qcheck-19.log is exact on all four scenarios.

  Follow-up diagnostic, qcheck-22.log / compare-20261028-043411-00875db2: at Jinae's failing call, the supplied output storage has vtable word 0, active advice 0 and target 0. Leaving it untouched again faults at +0x50E219. The replacement now initializes a native empty cRZString in this storage using the existing allocator-B string helper (SPEC-GAP), and uses a separate constructed-string helper for its own Lua callback. Please confirm the result-storage size/lifetime and empty-target contract in the spec and ABI row.

- **CS20 - §7 success-map write order.** Please specify the GUID hash, initial bucket hint, growth/chain order and whether Read reserves for its incoming count. The section requires hash-map order but gives none of those parameters. After the target-name construction fix, qcheck-23 is 3/4 exact; East Weburg is clean with only `0BB14381/299B2D1B/0` different (79 bytes including the class-store wrapper, ten successes). The replacement formerly wrote a BTreeMap in ascending GUID order. It now uses the existing STLport identity-hash model with its default hint 100 (193 buckets), marked SPEC-GAP, preserving insertion order and profile overwrites.
