- **LM4 - §3 retaining-wall construction:** please define box-to-cell edge ranges and inner/across-cell coordinates for each side, endpoint/traversal order, which positions receive 0.001 versus 0.002 m offsets, endpoint-specific ±0.2 m seam rules (especially terrain crossing the flat altitude), triangle splitting/diagonal/winding/count at equality/crossing, UV origin/u repeats, vertex lighting/colour calculation, and whether the across-edge flat test actually suppresses construction/draw. Current core can own edge bands, facing, texture and draw decisions but cannot truthfully produce the unspecified triangle buffer or recolouring. [unresolved]
  **ANSWERED 2026-10-23 (re-lotmodels-contracts4):** DIFFERS — [§3.2](../../lot-models.md#32-finite-wall-range-and-ordered-construction-lm4) and §8.1 define the valid finite domain and all four sides. Bias-and-bit nearby-integer ranges are not floor/ceil. Eligibility requires a terrain endpoint strictly above L; the flat neighbour test follows it. Three emit branches split against stored L−f32(0.2), without interpolating an intersection. The 0.001/0.002 constants alter reported bounds, not positions; y bounds use raw heights without seam overshoot. Ordered buffers grow without shortening, preserving an old tail. Lighting consumes explicit raw primitive outputs. Literal ledgers are UNEXECUTED natively; invalid/overflow domains remain LM8.

- **LM7 - §4 draw-state/combiner order:** please publish alpha/tinted draw-state fields not enumerated in §4, exact combiner initialization and per-mode operation/arguments, global-light/RGB units and evaluation order, flat-strip vertex alpha for each mode, whether alpha-pass filtering precedes or follows a zoom reload, and texture-failure/cache behavior. Does force-context value 8 bypass the translucent-pass skip? LM1 already covers unsupported modes and flat-path bypass. Core retains an effective mode/alpha combiner request, not an invented native combiner. [unresolved]
  **ANSWERED 2026-10-23 (re-lotmodels-contracts4):** DIFFERS — [§4.3](../../lot-models.md#43-owned-cell-draw-state-and-ordered-calls-lm7) and §8.2 publish exact value/mask words, initialized bytes, decoded owned tuple and ordered context/driver requests. Mode255 is the sentinel; explicit0 tints. Reload/recolour precede null-binding and pass checks; force8 cannot bypass return2. All RGB channels use global-light component0. Mode3 fallback halves unsigned alpha before multiplying stored 1/255; flat/delegated alpha keeps the original. Enum names for modes0–3 are grounded in the existing public driver contract; other mode meanings/upstream ownership remain LM1. No final device-state/pixel or native-execution claim.

- **LM3 - §2 foundation geometry and height math:** please specify vertex/face/UV order, UV origin/direction on each side/top, top-scale units and zero-scale behavior, footprint border sampling order/range, initial base/step count, and exact rounding/precision for `ceil((top-max(ground,water))/16)` (including equality at a step and fractional existing depth). Is top 40, ground 21, water 25 exactly one step (base 24), and does forced rebuilding at an unchanged base relight? Portable faces currently retain labelled extents/spans without a native buffer order.
  **ANSWERED 2026-10-22 (re-lotmodels-contracts4):** DIFFERS — [§§2.2–2.3](../../lot-models.md#22-foundation-sampling-and-step-arithmetic-lm3) give native quad order and x87/binary32 operations. Counts truncate `(depth+16)/16`, including for existing depth; exact multiples are not ceiling. Required count one only lowers to base 24 when the existing count is less than one. Forced rebuild does not relight. All sides use footprint width for u, including nonsquare sides; top scale has no zero guard.

- **LM5 - §§1–4 texture and draw failures:** does fallback happen for absent configuration, failed resource lookup, or both; is it retried even if primary equals fallback; are keys/cache zoom updated on failure; what happens on a second failure? Please specify foundation type/group and wall type, texture-ID sort meaning, top-only foundation draw when side binding fails, and wall/cell draw with no binding. What is key+zoom overflow behavior? The portable loader currently makes one primary attempt (if present), then one fallback on failure/absence; it records failed zooms without retry until zoom changes and skips draws requiring missing bindings.
  **ANSWERED 2026-10-22 (re-lotmodels-contracts4):** DIFFERS — [§2.1](../../lot-models.md#21-binding-failure-and-independent-top-draw-lm5), §3.1 and §4.2 specify requests, ownership and failure caching. Zero foundation/wall keys disable lookup; failed nonzero keys mutate to fallback, retry once even if identical, and remain null after a second failure. Cell zero key clears the binding successfully; nonzero keys try wrapped K+zoom then K without mutation. Foundation FSH group is `0x1ABE787D`, wall group `0x891B0E1A`, cell group `0x0986135E`, all type `0x7AB50E44`. Sort reads the first underlying texture word. Independent top draws survive side failure.

- **LM6 - §4 cell corners and placement:** publish the initial four-corner (position and UV) cycle, direction of orientation 1, whether mirroring occurs before/after rotation, flat strip order, terrain corner-altitude slot order, bounds height range for flat versus sloped placement, lighting colour representation, and update triggers for placement/colours. Portable callers must supply corner coordinates/cycle explicitly; no original-owner corner routine is a provider.
  **ANSWERED 2026-10-22 (re-lotmodels-contracts4):** DIFFERS — [§4.1](../../lot-models.md#41-corner-placement-and-update-contract-lm6) provides the native four-record strip, all orientation UV tables, postrotation mirror, terrain output slot order, bounds and BGRA bytes.
