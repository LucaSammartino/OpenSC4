# Interface (ABI) facts

These tables record how the game's virtual methods are **called**: the vtable slot, how many argument bytes the
callee pops, and which register carries the return value. They are generated by `tools/abi_extract.py` from the
target executable (SimCity 4 Deluxe 1.1.641, GOG). They are interoperability facts, not code: no instructions,
control flow or algorithms are recorded. **Engine authors may read and use them** (see
[CONTRIBUTING.md](../../CONTRIBUTING.md)).

| File | Contents |
|---|---|
| `interfaces.tsv` | Every interface the engine implements or calls (curated in `re/abi_interfaces.tsv`), one row per slot, using the original class that implements it |
| `vtables.tsv` | Every named vtable in the executable (853), for lookups beyond the curated set |
| `functions.tsv` | Every Ghidra-exported function plus vtable-only targets: entry convention, stack/register arguments, return channel and confidence (see below) |
| `layouts.md` | Field offsets of game objects that original code reads directly |
| `allocators.md` | Which allocator owns the memory of containers shared with the game (three separate pool instances) |
| `direct-calls.md` | Non-virtual game functions a replacement calls by address: convention, arguments, pop size, return channel and the expected `this` sub-object |

Columns:

| Column | Meaning | Reliability |
|---|---|---|
| `interface`, `game_class` | (`interfaces.tsv` only) the SDK interface and the original class whose vtable implements it | as good as the symbol port |
| `class`, `vtable` | (`vtables.tsv` names the class `class`) the named class; `vtable` = address of that vtable in the executable | address exact, name as good as the symbol port |
| `slot`, `offset` | vtable index and byte offset | exact |
| `target`, `method` | address of the original method and its ported name (`icf::` = identical-code-folded body shared by several methods; the name is one of them) | address exact, name as good as the symbol port |
| `callee_pop`, `arg_dwords` | bytes popped by the method's `ret N` = size of the arguments after `this` (`__thiscall`) | **exact**. An `int64`/`double` argument counts 8, everything else 4 |
| `ret` | `x87` = float/double in ST0. `edx:eax` = 64-bit integer. `eax-or-void` = 32-bit value, pointer, bool, or nothing. `via-call` = whatever a callee returned. `forward` = tail call through a pointer (ABI of the target). `pure` = `_purecall`. `unknown` can also be a method that returns nothing | `x87` high. `edx:eax` and `eax-or-void` medium. The rest low |
| `ret_confidence` | `high`, `medium` or `low`: how sure the extractor is of `ret` | as stated |
| `notes` | `inconsistent-pops`, `indirect-jump …`, `tail->…`, `truncated` | |

How to use them:
- A declaration whose argument bytes differ from `callee_pop` corrupts the caller's stack on every call.
- A method declared `float`/`double` must have `ret = x87`, and a method with `ret = x87` must be declared
  `float`/`double`.
- `int64` returns must have `edx:eax`.
- **SDK declarations the game does not match** (the game is binding; a plugin built on the SDK form corrupts the stack
  in the original too): `cISC424HourClock` slots 7 `GetTimePercentage` and 9 `GetVisualTimePercentage` take a `float*`
  out and pop 4 (`ret 4` at `0x0044543E`, `0x0044546E`; SDK `float (void)`), slot 19 `GetEventHour` takes a dword index,
  not a `bool`, and slot 20 `GetTimeMagnification` returns the float's bits in EAX (clock24.md §8, CK6).
- `eax-or-void` does not tell a pointer from a bool or a value: the spec decides that.
- **A float/double declaration on a method the game treats as `eax-or-void` corrupts the x87 register stack.**
  If the game calls our method, every call leaves one value on the game's x87 stack that nothing removes; after
  eight, the next load overflows and gives NaN (all x87 exceptions are masked in-game), and NaN converted to an
  integer is a garbage size or index. If we call the game's method through such a declaration, our code pops a
  value that was never pushed (underflow, NaN). Both directions are invisible until something reads the NaN.
- How `ret = x87` is decided (corrected 2026-10-14, after the run 74 audit): the x87 stack depth is followed
  forward from the entry along every path to each `ret` (0 at entry; at every call the depth is 0, then 1 if the
  code after the call uses a value the call left). Depth 1 at the `ret` = returns in ST0. A function whose last x87
  instruction stores and pops (`fstp [mem]`) returns nothing in ST0, even though it ends in float code. Earlier
  tables tagged such functions `x87`; 63 interface rows (and 105 vtable rows) were corrected, among them
  `cISC4Demand` 16/17, `cISC4DemandSimulator` 8, `cISC4WeatherSimulator` 11, `cIGZVariant` 41, the
  `cISC4RegionalCity` setters 51–63, `cISC4SimGrid` 20/21 and `cISC4OccupantManager` 14–18.

Regenerate with `python tools/abi_extract.py bin/SimCity4.exe`. The tool is analysis-side tooling; only its output
is for engine authors.

> **Warning: do not regenerate `interfaces.tsv` yet.** It carries hand corrections that are not in
> `re/abi_interfaces.tsv` or in the extractor: commits 7d2f368, 83aa768, a9eef99, bbee494 and 402072f, including eight
> interface pairs added by hand. A blind regeneration silently reverts them, and the table feeds the ABI conformance
> test. Move the corrections into the curated input (or the extractor) first. The modal-dialog rows
> (`cIGZWinMgr`, `cIGZWin`, `cIGZMessageServer`, `cIGZMessageTarget(AudioEventHandler)`, see
> `docs/specs/modal-dialogs.md`) are in the curated input, but their `re-modal:` notes are hand-written and a
> regeneration drops them.

## Slot counts: vtables longer than the declaration

The ABI conformance test (`engine/tests/abi_conformance_test.cpp`) checks every declaration the plugin implements or
calls against this table, slot by slot, and also checks that the declaration has as many slots as the table. A
game vtable is often longer than the SDK interface. The extra slots fall into three cases:

1. **Interface methods the SDK header lacks** (for example `cISC4TutorialSystem` slots 18-20, tutorial.md §6): a
   caller may reach them through the interface, so declare them. Write a class in our own interface header that
   derives from the SDK interface and declares only the missing slots (`cFC4ISC4TutorialSystem` in
   `engine/plugin/FC4Interfaces.h`). Then list that class in `engine/tests/gen_abi_entries.py` in place of the SDK
   class. The derived class checks the SDK's own declarations of the earlier slots, so code that calls them through
   the SDK pointer stays covered. Call the new slots only through the derived class (`fc4::AsGame`).
   When the SDK header instead declares more slots than the table lists, or declares one of them wrongly,
   declare the interface as compiled up to the table's last slot in a class of our own deriving from
   `cIGZUnknown`, and list it next to the SDK class (`cFC4IGZCommandParameterSet`, slots 3-10: the SDK's slot 10
   takes an `int32_t`, the game's a `cIGZVariant const&`). The SDK class keeps its row, with a reviewed entry,
   while plugin code calls it.
2. **A trailing deleting destructor** (the trailing destructor rule). This covers a table with exactly one slot more
   than the declaration, where that slot is the implementing class's scalar deleting destructor: its method is
   named `~…` or `…deleting…`, and it pops 4 (the flags dword). The test accepts this without a review entry and
   prints a `dtor` line. The reason: the SDK interfaces declare no virtual destructor, so MSVC places the class's
   destructor after the interface's last method. Only the class's own `Release` calls it, on its own object. No
   caller reaches it through the interface, and an object FreeCity4 implements is never destroyed through it. This
   rule covers `cISC4OccupantManager` 49, `cISC4PropManager` 40, `cISC4LotConfigurationManager` 28,
   `cISC4LotConfiguration` 33, `cISC4TrafficSimulator` 43, `cISC4PathFinder` 33, `cISC4Demolition` 12,
   `cISC4AuraSimulator` 16 and `cISC4FloraSimulator` 25. The rule's own cases run first in the test
   (`rule self-test` line).
3. **Anything else** needs a reviewed entry in `kReviewedSlotCounts` with the reason. Examples: two or more extra
   slots, a gap, an unnamed slot, a destructor that pops nothing (an ICF'd tail call), or class-private virtuals.
   The entry is keyed on both counts, so a regenerated table with different counts fails again. Reviewed entries are
   checked before the rule, so do not add one for a case the rule covers.

A declaration that is longer than the table is always reported.

The listing the test decodes its slots from, `engine/tests/abi_entries.inc`, is generated by
`engine/tests/gen_abi_entries.py` and is not checked in: the CMake target `fc4_abi_entries` regenerates it on
every build and the test depends on it, so a stale listing can never be compiled. With no Python 3 the test is
skipped rather than compiled against whatever is on disk.

`cIGZCommandParameterSet` is case 3: the SDK declaration has 15 slots and the table has 11 (rows for 3, 5-8 and
10 only), so it keeps a reviewed entry in `kReviewedSlotCounts`. Slots 4 and 9 have no rows and 11-14 are the
SDK's own trailing methods; `cFC4IGZCommandParameterSet` (slots 3-10) is the declaration the plugin calls
through. Both check out as `ok`.
